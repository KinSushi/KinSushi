# Non-Goals

This file documents what the public GitHub portfolio must not become.

---

## Do not add more strategy without code

Avoid extending documentation indefinitely. Every strategic document must support an executable or reviewable technical project.

Priority is now:

1. runnable DataOps repo;
2. runnable MLOps repo;
3. sanitized Jedha evidence;
4. migration-quality repo;
5. secure RAG repo.

---

## Do not publish application material

Never publish:

- CVs;
- cover letters;
- job trackers;
- recruiter messages;
- salary targets;
- company-specific application notes;
- interview scripts;
- private school documents;
- certificates with personal identifiers;
- contracts, invoices or CPF documents.

---

## Do not center trading automation

Market-data engineering or backtesting infrastructure can be documented as technical evidence, but public positioning should not center on:

- live trading claims;
- automated trading performance;
- investment advice;
- “AI trading bot” language;
- salary projections;
- long-term quant compensation targets.

For Swiss regulated finance, the safer public signal is:

> Data quality, monitoring, risk analytics, model governance, infrastructure and production reliability.

---

## Do not publish private or sensitive data

Never publish:

- real banking data;
- real client data;
- private documents;
- real account numbers;
- credentials;
- API keys;
- hostnames;
- IPs;
- license keys;
- screenshots with identifiers.

---

## Do not overclaim certification status

Use conservative wording until every certification is officially validated.

Allowed:

> Jedha RNCP Level 6 / Level 7 track.

Allowed when evidence is ready:

> Public technical evidence mapped to RNCP35288 blocks.

Not allowed until complete:

> Certified Architecte IA.

Not allowed if unsupported:

> Master degree.

---

## Do not make notebooks the final product

A notebook can explain analysis, but portfolio repos should include:

- scripts;
- tests;
- CLI or API entrypoints;
- Docker or reproducible setup;
- documentation;
- runbooks;
- quality controls.

---

## Do not ignore visual quality

Every public repo must be readable, structured and visually clean. Use:

- badges;
- diagrams;
- tables;
- concise README sections;
- screenshots or sample outputs;
- clear non-goals.
